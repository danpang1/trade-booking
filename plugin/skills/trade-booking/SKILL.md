# Trade Booking — CASHFLOW + SPOT

## When to activate

The user wants to book one or more trades — CASHFLOW, SPOT, or a mix:
- "book a $500K OPEX to TOKKA TREASURY" (CASHFLOW)
- "submit these 6 cashflows from the Slack thread" (CASHFLOW batch)
- "swap 1,000,000 USDC to 1,000,000 USDG on Paxos @ 1.00" (SPOT)
- "buy 0.5 BTC at 70000 on Binance" (SPOT)
- "/tokka-mo:trade-booking"
- a paste mixing cashflows and swaps (mixed batch)

LOAN / LOAN REPAYMENT cashflows and SPOT amendments still go through the
Middle Office web form — this skill creates new CASHFLOW and SPOT drafts only.

## Hard rules

1. **You never make HTTP calls.** Everything goes through the bundled CLI at
   `${CLAUDE_PLUGIN_ROOT}/bin/tokka-mo`. Always use that full path — never bare
   `tokka-mo`, because PATH setup is not guaranteed for non-engineer installs.
2. **Show a structured preview AND get explicit `y` before submitting.** Never
   submit on first parse. Never assume.
3. **Validate against the local refdata cache.** If a value isn't in the live set,
   STOP and ask — don't guess at the closest match. **Do NOT run `refdata refresh`
   as a warm-up.** `book` and `book-batch` load refdata themselves and re-fetch
   automatically once the cache is over 24h old, so a manual refresh before
   booking buys nothing and costs the user a few seconds of network round-trips
   while they wait. Only refresh when a value the user insists is valid comes
   back as "not in refdata" — see the troubleshooting table.
4. **One `client_request_id` UUID per draft, generated by `tokka-mo`.** Don't
   manually mint one. If a submit fails and the user wants to retry, reuse the same
   CRID — passing a fresh UUID on retry creates a duplicate draft.
5. **CASHFLOW or SPOT only.** Anything else (loans, amendments) → web form.
6. **Never invent, default, or blank a mandatory field.** Every field the MO web
   form marks `*` must carry a real, user-supplied value before you submit. If one
   is missing — counterparty, account, asset, amount, dates, anything — STOP and
   ask the user for it. Do not substitute a placeholder, do not fall back to a
   "safe" default like `TOKKA TREASURY`, do not send an empty string, and do not
   proceed on the grounds that the server or the CLI would accept it. The server
   is more permissive than the web form: a draft that passes the API but is
   missing a `*` field cannot be opened and approved in the form, so it strands
   in PENDING_REVIEW. Asking one extra question always beats a stranded draft.

## Workflow

1. **Parse the user's input** into a list of trades, tagging each as CASHFLOW or
   SPOT. For CASHFLOW extract the fields in `references/cashflow-schema.md`; for
   SPOT extract the fields in `references/spot-schema.md`.
2. **Identify missing mandatory fields** (the `*` list below). Ask the user to
   supply them — one round of questions, batched, before any preview. Never guess
   a value and never leave one blank.
3. **Validate** against the cached refdata. For SPOT: `portfolio_id`,
   `portfolio_name`, `base_asset`, `quote_asset`, `account`, `counterparty`, and
   (if given) `fee_asset`. If anything's missing or wrong, ask the user.
4. **Show a structured preview** in a code block. For batches, number the rows and
   group them by category (`CASHFLOW (n)` / `SPOT (n)`).
5. **Ask: "Submit? (y/N)"** — wait for an explicit `y`. Anything else is a no.
6. **On `y`**: shell out. Single trade →
   `${CLAUDE_PLUGIN_ROOT}/bin/tokka-mo book --category <CASHFLOW|SPOT>`. Two or more
   (including mixed) → `${CLAUDE_PLUGIN_ROOT}/bin/tokka-mo book-batch`, with each
   trade carrying its own `"category"`. Report draft IDs + the review URL.

## Mandatory (`*`) fields — must come from the user

These mirror the MO web form's own validation, which is what a reviewer hits when
they open the draft. Anything here that the user has not given is a question, not
a default.

**CASHFLOW** — `cashflow_type`, `direction`, `portfolio_id`, `counterparty`,
`account`, `account_type`, `asset`, `amount`, `trade_date`, `value_date`.
Plus `network` when `account_type = WALLET`.
Plus `product` whenever the account offers one — see below.

**SPOT** — `direction`, `portfolio_id`, `base_asset`, `base_amount`,
`quote_asset`, `quote_amount`, `price`, `counterparty`, `account`,
`account_type`, `trade_date`, `value_date`.
Plus `product` whenever the account offers one — see below.

Derived, so never ask: `entity` and `portfolio_name` (from the portfolio's
refdata row), `user_id` (the logged-in user), `status` (`PENDING`).

If the user gives a value that isn't in refdata, that is also a question — say
what they gave, show the near matches, and let them pick. Never silently snap to
the closest one.

## Loan-related cashflows — hand over to `loan-booking`

If `cashflow_type` is `LOAN`, `LOAN REPAYMENT`, `INTEREST EXPENSE`,
`INTEREST INCOME`, `MARGIN LOAN` or `MARGIN REPAYMENT`, the cashflow almost
always settles against a **master loan agreement** (an `MLA…` deal ref) and
should be tagged to it via `_meta.loan_deal_refs`. An untagged loan repayment
leaves the facility looking unpaid.

Use the **loan-booking** skill for these. Do not book one untagged just because
the user did not mention a facility — look it up first:

```bash
python <cli> loan-list --counterparty <name> --asset <ticker>
```

Booking the cashflow itself is unchanged; the mapping is one extra key on the
same payload.

## SPOT specifics

### Swap → SPOT mapping (the canonical convention)

A swap is *"give A, receive B"*. The received asset is the **base**, and the
direction is **LONG**:

- `Swap <amtA> <A> to <amtB> <B> [on <venue>] [@ <price>]` ⇒
  - `direction = LONG`
  - `base_asset = B`, `base_amount = amtB` (what you receive)
  - `quote_asset = A`, `quote_amount = amtA` (what you give)
  - `price` = quote-per-base. If omitted, derive it as `amtA / amtB`.
- Enforce `base_amount × price == quote_amount`. For a 1:1 stablecoin swap the
  amounts are equal and `price = 1.0`.

"buy/sell" phrasing maps directly: **buy** X = LONG X (X is base), **sell** X =
SHORT X.

### Auto-fill and defaults

- `entity` and `portfolio_name` are read from the refdata portfolio row for the
  given `portfolio_id` — don't ask the user for them.
- `portfolio_id` is the user-facing PTF **number** (e.g. 8041), emitted as an int.
- Omit `txn_type` (the server defaults it to `SPOT`); set `status = PENDING`;
  `user_id` is stamped by the CLI from the logged-in user.

### Account AND counterparty are both mandatory for SPOT

Neither may be omitted. Do not treat either as optional, and never emit a line
like "counterparty omitted — optional for SPOT": if you don't have one, that is a
question for the user.

Be aware that permissiveness further down the stack is not permission. The API
accepts a SPOT draft with no `account` and no `counterparty`, and the web form's
own client-side check only enforces Account Name — but every SPOT trade has a
venue and a party on the other side, and a draft missing either is not reviewable.

- `account` — if the user names a venue ("on Paxos"), resolve it to that venue's
  refdata account and set `account_type` to match. Otherwise **ask which
  account**. `account_type` is `EXCHANGE`, `WALLET`, or `BROKER`, and the account
  must exist in refdata.
- `counterparty` — must be a NAMED counterparty in refdata, spelled **exactly**
  as `counterparty-list` prints it. The server rejects anything else (free text,
  a different case, an abbreviation) and stamps `counterparty_id` itself from
  refdata — never invent or pass a CID. For an internal SPOT between two Tokka
  portfolios it is the other portfolio's number. If the user hasn't said who the
  trade faced, **ask**; if their wording matches no refdata name, show the
  closest names and ask them to pick, do not guess.

### `product` — the gateway sub-account, mandatory wherever there is a choice

Every trade records an `account_id`, and the server derives it from
`account` + `product`. Book without a product and the trade lands with a NULL
`account_id`: it is attributed to the venue but not to the sub-account, and the
position and fee feeds cannot line it up. So `product` is a mandatory field, not
a nicety.

What it means depends on the account type, and the valid values come from the
account's own refdata record — never invent one:

| `account_type` | `product` is | Source |
|---|---|---|
| `EXCHANGE` | the trading product — `SPOT`, `USDT_FUTURE`, `PORTFOLIO_MARGIN`, … | the account's `products` |
| `WALLET` | the **chain** — `ETHEREUM`, `SOLANA`, … | the account's `chains` |
| `BROKER` | fixed; omit it | — |
| `BANK` | none; omit it | — |

**Resolve it in this order, and only ask when none of these settle it:**

1. **The user said which.** "on the futures account", "via Arbitrum" — use it,
   after checking it is in the account's list.
2. **The account offers exactly one.** Use it. Roughly half of all exchange
   accounts and 184 wallets are in this case.
3. **WALLET with a `network`.** For a wallet booking the network IS the chain,
   so `product` = `network`. Do not ask twice for the same fact.
4. **A SPOT trade on an exchange** — take the first that the account offers, in
   this order: **`SPOT` → `UNIFIED` → `DERIVATIVES`**.
5. **Otherwise ASK.** Show the account's options and let the user pick.

Two cases that reach step 5 and must NOT be guessed:

- **A CASHFLOW on a multi-product exchange account.** There is no sensible
  default — a funding fee and a spot settlement belong to different
  sub-accounts. Ask.
- **An exchange account offering only `FUNDING` / `TRADING` / `FUTURES`**
  (the OKX and KuCoin accounts). `TRADING` shares gateway code `001` with
  `SPOT`, which makes it *look* like the obvious answer, but it is a distinct
  product and picking it silently would mis-file the trade. Ask.

If the account's refdata carries no options at all, omit `product` — there is
nothing to choose and the gateway rule handles it.

## Common patterns

### OPEX payment (CASHFLOW)
- cashflow_type `OPEX`, direction `OUTGOING`, counterparty = the vendor, which
  must exist in refdata. If the vendor isn't catalogued yet, STOP and ask the user
  how to proceed — booking it against `TOKKA TREASURY` misattributes the spend and
  someone has to unpick it later.

### Inter-portfolio funding (CASHFLOW)
- cashflow_type `INTER PTF FUNDING`; book both legs (OUTGOING from source,
  INCOMING into dest); counterparty = the *other* portfolio's number string.

### Stablecoin / FX swap (SPOT)
- e.g. USDC → USDG @ 1.00: `direction=LONG`, `base=USDG`, `quote=USDC`,
  `base_amount=quote_amount`, `price=1.0`.

## Errors you'll see

| Error | What it means | What to do |
|---|---|---|
| `not logged in` | Stale CLI session | Run `tokka-mo login` |
| `Token rejected — run: tokka-mo login` | 401 from server | Re-login |
| `required field missing or empty: X` | Validation gap | Ask user to supply X |
| `X not in refdata` | Stale cache or typo | `tokka-mo refdata refresh`; if still missing, ask user. |
| `base x price ... must equal quote_amount` | Inconsistent SPOT amounts/price | Recompute one of base/quote/price with the user. |
| `base_asset and quote_asset must differ` | Same asset both legs | Fix the pair. |
| `cannot reach <url>` | Network / VPN issue | Tell user; don't retry blindly. |
